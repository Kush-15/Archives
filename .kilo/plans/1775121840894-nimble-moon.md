# Razorpay Payment Pipeline Stabilization Plan

## Objective
Fix payment failures and the white `about:blank` Razorpay popup **without breaking existing frontend behavior** (buttons, scrolling, cart overlay, search, routing).

## What this plan targets
- Razorpay credential correctness and mode consistency (test vs live)
- Frontend checkout modal initialization and callback behavior
- Backend order/payment verification correctness and idempotency
- Static asset build/deploy stability so frontend does not regress after payment fixes
- Safe rollout with reproducible tests and rollback checkpoints

## Known high-probability failure points (from current code audit)
1. `Checkout.tsx` cancels orders in `modal.ondismiss` unconditionally; this can race with success handler and flip paid orders to cancelled/failed.
2. Razorpay `prefill` omits `email`; some payment methods are stricter and can fail unexpectedly.
3. `create_order` uses `int(total * 100)`; should be Decimal-safe paise conversion.
4. Production template `Archives/templates/index.html` hardcodes hashed JS/CSS filenames, so frontend can desync after rebuilds.
5. Environment drift risk: keys and webhook secret can be missing/mismatched across local/staging/prod.

## Phase 2 - Backend correctness hardening

### 2.1 Decimal-safe amount conversion
- In `create_order`, compute paise using Decimal-safe conversion, e.g. quantize to 2 decimals then convert to integer paise.
- Reject non-positive totals defensively.

### 2.2 Validation hardening
- Validate each cart line:
  - `product_id` non-empty
  - `quantity` integer and `>= 1`
- Return structured validation errors for frontend display.

### 2.3 Idempotent state transitions
- In `verify_payment`, if order already `paid`, return success idempotently (avoid duplicate processing).
- Ensure stock restore happens only once on failure/cancel paths.

### 2.4 Better diagnostics
- Add structured logs for:
  - create-order request/response IDs
  - Razorpay API exceptions
  - verify signature outcome
  - cancel reason and status transition

Acceptance criteria:
- Backend consistently returns correct `amount` (paise int), `currency`, and handles repeats safely.

## FIX PHASE (with diagnosis confirmed)

**Root cause: Razorpay SDK getting 400 Bad Request when trying to create payment session**

### Phase A: Validate order data being sent to Razorpay
1. **Check amount format in Checkout.tsx:**
   - Is it sent as integer paise? (e.g., 260000 for ₹2600)
   - Or as float? (e.g., 2600.00)
   - Razorpay requires integer paise, no decimals

2. **Check currency in Checkout.tsx:**
   - Must be exactly "INR" (uppercase)
   - Verify it matches backend response

3. **Check order_id format:**
   - Backend returns: `razorpay_order_id=order_SZ7...`
   - Frontend must send this exact string to Razorpay, not modified
   - Check no truncation or encoding issues

4. **Verify key_id consistency:**
   - Frontend gets key from `/api/payment/key/` endpoint
   - Backend creates order with same key
   - Confirm they match exactly: `rzp_test_SW91Chvw8PXXqH`

### Phase B: Check Razorpay test account configuration
1. **Is test account properly set up?**
   - Test mode is enabled in Razorpay Dashboard
   - Test cards are available
   - No restrictions on order amount/currency

2. **Is the order already in a bad state?**
   - Check Razorpay Dashboard → Orders
   - See if orders appear but are in wrong status (captured, partially paid, etc.)

### Phase C: Fix the issue
**Most likely fix:** Amount is being sent as float instead of integer paise
- Checkout.tsx sends `amount: preCreatedOrder.amount` 
- Verify backend is returning amount as integer (260000, not 2600.00)
- If backend returns float, convert in frontend before passing to Razorpay

**Secondary fix:** Currency casing or order_id format issue
- Ensure order_id from backend is passed exactly as-is
- Ensure currency is uppercase "INR"

### Phase D: Rebuild and test
1. Fix the issue (likely amount format)
2. Rebuild frontend
3. Test payment flow again
4. Verify Razorpay SDK no longer gets 400
5. Confirm about:blank popup is gone

- Failed/cancelled payments restore stock exactly once.

## UPDATE: ROOT CAUSE IDENTIFIED

**Browser Console Error (Critical):**
```
api.razorpay.com/v1/standard_checkout/payments/create/ajax?key_id=rzp_test_SW91Chvw8PXXqH&session_token=... 
→ 400 Bad Request
```

**What this means:**
1. Frontend successfully calls `/api/payment/create-order/` ✅
2. Backend successfully creates order on Razorpay ✅ (logs show: "razorpay_order_id=order_SZ7...")
3. Frontend receives valid order_id and passes to Razorpay SDK ✅
4. Razorpay SDK tries to create payment session with the order ❌ **FAILS WITH 400**
5. Razorpay SDK's error handler triggers the about:blank popup as fallback

**Why the 400?**
One of these values sent to Razorpay is invalid or mismatched:
- **Order ID format** - Is it in correct Razorpay order format?
- **Amount** - Is paise conversion correct? (should be integer, no decimals)
- **Currency** - Is it exactly "INR"?
- **Key ID** - Does it match the order's key_id on Razorpay's side?
- **Order state** - Has the order already been captured/processed?
- **Razorpay account config** - Is the test account properly configured?

**Other non-critical errors in console:**
- CORS header access denied (x-rtb-fingerprint-id, request-id) - Razorpay SDK issue, not ours
- Permissions policy violations - From Three.js/animation libs, not payment related
- Mixed content warning - Local network HTTP resource
